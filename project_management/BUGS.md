## Resolved Bugs

| ID | Description | Severity | Resolution |
| :--- | :--- | :--- | :--- |
| **BUG-001** | Colorblind mode (`setting-colorblind`) only recolored the spheres and tether line — glows (`--glow-cyan`/`--glow-magenta`) and obstacle backgrounds stayed the original hue, since they were static `rgba()` values instead of derived from the active neon color. | Medium (accessibility) | Fixed: glow shadows are now computed dynamically from the active color via `setNeonColors()`; obstacle backgrounds use `color-mix()` against the CSS variables. |
| **BUG-002** | No progress persistence — crystals, owned skins, best score, and settings reset to defaults on every page reload. | Medium | Fixed: added `localStorage`-backed `saveProgress()`/`loadProgress()`. |
| **BUG-003** | The "Global Leaderboard" on the Events screen was fully hardcoded HTML with no connection to actual gameplay — the player's row never changed after a run. | Low | Fixed: `renderLeaderboard()` now rebuilds the list from real `state.bestScore` against fixed flavor NPC scores. |
| **BUG-004** | `moveAndCollide()` in `prototype/app.js` re-checked every obstacle's collision distance every frame it stayed within the `GRAZE_BAND` (~9 frames at the run speed used), so a single safely-passed obstacle could call `triggerGraze()` — and bump the combo — multiple times instead of once. Found while porting the mechanic 1:1 to `godot/scripts/gameplay.gd`. | Low (game feel / scoring) | Fixed in the Godot port: each obstacle dictionary gets a `resolved` flag set the first time it's checked in-band, so collision/graze only evaluates once per obstacle. The browser prototype still has the original behavior (not touched, since Phase 10 supersedes it). |
| **BUG-005** | `main.gd`'s `_show_sub_screen()` (Shop/Achievements/Settings/Events) instantiated each screen's root `Control` with no explicit size. A fresh `Control` defaults to a 0x0 rect; its own anchors resolve against the viewport (its parent is a `CanvasLayer`, not a `Control`), but its *children*'s anchors resolve against that 0x0 rect — so every full-rect/full-width child inside the screen (background `ColorRect`, header bar) collapsed to 0x0 too, and the Main Menu screen showed straight through underneath. Only visible with real rendering — the headless script-error check couldn't catch it. | High (visual) | Fixed: `screen.set_anchors_preset(Control.PRESET_FULL_RECT)` right after instantiating each screen in `main.gd`. |
| **BUG-006** | `UIHelpers.label()` enabled `autowrap_mode` on every label by default. A wrapping `Label` reports a much smaller *minimum* size to its parent container than its natural single-line width — so a short "badge" label with no explicit `custom_minimum_size` (e.g. the achievement reward tag "💎 200") could get squeezed to a sliver by a wider sibling in the same row and wrap into an unreadable vertical stack of single characters. | Medium (visual) | Fixed: autowrap is now opt-in (`wrap: true` param, default `false`); call sites with genuine paragraph text (achievement/upgrade descriptions, the settings "about" text, mission labels) opt in explicitly and set their own width. |
| **BUG-007** | Simplifying `project.godot` from two renderer keys (`renderer/rendering_method` + `renderer/rendering_method.mobile`, both `"gl_compatibility"`) down to just the base key silently reverted Android to the `mobile`/Vulkan renderer — exactly the one ENV-001 shows failing to present on this emulator. The Android runtime specifically reads the `.mobile`-suffixed override (matching what the Android exporter's own C++ reads at export time for its Vulkan-requirement check); the un-suffixed base key alone doesn't reach it, even though export-time settings-file inspection (`assets/project.binary`) showed the correct value either way. Confirmed via `adb logcat`'s `renderer: mobile (ProjectSettings)` line reappearing after the "simplification," and via `adb install`'s incremental-install path serving stale content on top of that, which cost real time to rule out as a separate cause. | `godot/project.godot`, Android builds only (desktop reads the base key fine) | Fixed: restored both keys. Lesson for later: don't "clean up" a project setting that came out of live-tested trial and error without re-testing — the two keys looked redundant, but weren't. |
| **BUG-008** | The shop's "not available yet" info dialog (`AcceptDialog`, shown when tapping a real-money item) had neither autowrap nor a set width, so a long `dialog_text` overflowed past the panel instead of wrapping, and the dialog's own OK button ended up positioned outside what was actually visible/tappable — a real softlock. Found on a live Android playtest: tapping a $-priced item opened a dialog with no reachable way to dismiss it by touch; the only escape was the Android system back button, which exits the whole app instead of just the dialog (Godot doesn't intercept it to close the topmost popup by default). | `godot/scripts/screens/shop_screen.gd`, any real-money shop item, all platforms (worse on Android/touch since there's no keyboard Escape fallback) | Fixed: `_info_dialog.dialog_autowrap = true` and a fixed `min_size` so the text wraps and the dialog sizes to fit both the message and its OK button. Re-verified on Android: text wraps correctly, OK button visible and dismisses the dialog. |
| **BUG-009** | Side/cyan obstacles could never actually kill the player, no matter what action was taken — a genuine core-mechanic bug, not a visual one. The collision check needs `player_left_x < SIDE_SAFE_MARGIN` (110) or the mirrored check on the right, where `player_left_x = CANVAS_WIDTH/2 - width/2`. But `MAX_WIDTH` (the widest the tether could ever get, on hold) was 140, capping `width/2` at 70 — so the best-case `player_left_x` was `225 - 70 = 155`, 45px short of the 110 threshold. The tether physically could not reach far enough to cross into the side obstacle's danger zone, on either side, under any input. This was present in the original browser prototype too (`prototype/app.js` uses the identical formula and thresholds on the same 450px-wide canvas), not something the Godot port introduced — found only because the user pointed out that clicking/holding in a live test never visibly moved the sphere anywhere near an obstacle's edge, which turned out to be literally true rather than just a presentation issue. | `godot/scripts/gameplay.gd`, every run — cyan obstacles were purely decorative | Fixed: raised `MAX_WIDTH` from 140 to 290, so a full split now reaches `player_left_x = 80` / `player_right_x = 370` — 30px past the 110/340 thresholds on each side (matching the margin `MIN_WIDTH` already gives the center/magenta side of the mechanic). Verified two ways: an in-engine test directly driving `_move_and_collide()` with contrived obstacle/width states (wide-vs-side now collides, narrow-vs-side is safe, narrow-vs-center still collides, wide-vs-center still safe — all 4 cases pass), and a rebuilt tutorial briefing that now visibly shows the sphere reaching and overlapping each obstacle's edge in the "wrong" pose. The browser prototype (`prototype/`) has the same bug but wasn't touched, since Phase 10 supersedes it (same precedent as BUG-004). |

| **BUG-010** | Haptic feedback (`_haptic()` in `gameplay.gd`, called on crash and crystal collection) failed silently on every Android build so far: `adb logcat` showed `SecurityException: VIBRATE permission not found. Make sure it is declared in the manifest or enabled in the export preset.` on every attempted vibrate call. Godot's non-advanced export preset (the default `advanced_options=false`) doesn't request the VIBRATE permission automatically — it has to be turned on explicitly. Found during the live playtest of the rebuilt APK after the difficulty/combo/tutorial/BUG-009 changes; didn't crash anything (Godot's native bridge catches the exception and just logs a warning), so it was easy to miss without checking logcat specifically. | `godot/export_presets.cfg` (gitignored, machine-local), all Android builds up to this point | Fixed: set `advanced_options=true` and `permissions/vibrate=true` in the local export preset, re-exported, reinstalled, and confirmed via `adb shell dumpsys package` that `android.permission.VIBRATE` is now declared and granted, and via logcat that a real in-game crash no longer logs the SecurityException. Documented as a required setup step in `README.md`, since `export_presets.cfg` itself isn't committed. |

*Note: BUG-001 through BUG-003 were prototype (browser) bugs, already fixed there. BUG-004 through BUG-010 were found and fixed in the Godot port — BUG-005 through BUG-010 specifically were only caught by actually running the build (an in-engine screenshot test, a real Android install, or a live playtest), not the headless parse/runtime check, which is worth remembering next time something "loads with zero errors" gets called done. BUG-009 in particular was only found because the user distrusted a "looks fine" visual pass and pushed on a specific detail (the sphere not visibly reaching an obstacle's edge) until it turned out to be a real math bug, not a rendering nitpick. BUG-010 was only found by checking logcat during a live playtest — it doesn't crash or show visually, it just silently does nothing.*

## Environment Limitations (not app bugs)

| ID | Description | Where it shows up | Notes |
| :--- | :--- | :--- | :--- |
| **ENV-001** | First observed with the emulator forced into pure software rendering (`-gpu swiftshader_indirect`): the Android debug APK installed and its Godot engine fully initialized (autoloads, main loop, zero crashes — confirmed via `adb logcat`), but the on-screen frame stayed black. Two renderer-specific failures, neither touching Neon Tether code: `mobile` (Vulkan) failed every present call (`Couldn't present to Vulkan queue`, VkResult 5) against the emulator's software Vulkan (`llvmpipe`); `gl_compatibility` got past that but failed to compile Godot's own built-in scene shader (`GL_MAX_FRAGMENT_UNIFORM_VECTORS` exceeded) against SwiftShader's lower GLES3 uniform budget. **Resolved for real rendering**: relaunching the same emulator with actual host GPU acceleration (`-gpu host`, using the machine's Intel UHD 620 via Vulkan 1.3) fixed `gl_compatibility` completely — full menu, gameplay, collision, and game-over screens all render correctly (2 full runs played via `adb input`, best score persisting across them: 40m → 41m). `mobile` (Vulkan) *still* failed to present even with real hardware behind it, which points at the Android Emulator's own Vulkan swapchain integration specifically, not a GPU capability issue. | Observed on the `Monarch_Test` AVD, both software- and hardware-GPU emulator modes | **Action taken:** the project's renderer is now committed as `gl_compatibility` (`project.godot`) — confirmed working on this hardware-accelerated emulator; still recommended to re-confirm on a real device before shipping, since GL Compatibility and Vulkan-Mobile can behave differently across real device GPU/driver combos. |

*Kept in a separate table from the bugs above on purpose — these are dev-sandbox/tooling constraints observed while building, not defects to "resolve" in the project's own code.*
